## Pipeline (对齐 UniTime 论文)

所有模型统一: **2fps dense 采样 → vision encoder → token compression (resize_feature, N_total=12288) → combine_timestamps (CLIP_LENGTH=-1) → LLM LoRA**

| 模型 | native tokens/frame | 压缩后 tokens/frame | 2fps 帧数 (60s video) | 总 visual tokens |
|------|-------|-------|------|------|
| Qwen2-VL-2B | ~64 (adaptive) | ~64 (smart_resize) | ~120 | ~7680 |
| Gemma3 4B | 256 | ~81 (9×9) | ~124 | ~10044 |
| Gemma4 E4B | 256 | ~81 | ~124 | ~10044 |
| Qwen3-VL-2B | ~300 | ~81 | ~124 | ~10044 |

N_total=12288 (不是论文的 16384) 因为要留 ~4K 空间给 text tokens (timestamps + prompt + query) 和 backward 显存.

### v2 实验 (May 3) — 对齐 UniTime pipeline

2fps dense + token compression (N_total=12288) + combine (CLIP_LENGTH=-1).
v1→v2 区别: v1 固定 32 帧无 compress 无 combine; v2 按视频长度动态采帧, bilinear 压缩 token 数, combine 分段.

| Qwen2-VL-2B (CL=-1) | — | — | — | — | — | — | — | |

**v1 vs v2 Gemma3 4B 对比:**
- v1: 32帧 × 256 tok/fr = 8192 visual tokens, 无 combine → F1@10=63.3%, 25m
- v2: ~124帧 × ~81 tok/fr = ~10K visual tokens, combine ~42 timestamps → F1@10=50.5%, 44m
- v2 帧数更多但每帧分辨率降低 (256→81), 且 combine 把多帧合到一个 timestamp 下. F1 下降 13 点, 可能因为 token compression 损失了空间信息.

## 已知问题

### combine_timestamps + CLIP_LENGTH=32 不适用 GTEA

UniTime 上游 `CLIP_LENGTH=32` 为长视频设计. GTEA 短视频 (~120帧) combine 后只剩 2-5 个 timestamp → 精度崩溃.
代码默认 `clip_length=-1` (auto: T//num_clips) 才合理. 所有 scripts 已改为 -1.

### v1 实验未对齐 pipeline

v1 的 Gemma3/4/Qwen3 用固定 32 帧无 combine, Qwen2-VL 用 dense+combine(CL=32). 不在同一基准上. v2 统一对齐.
